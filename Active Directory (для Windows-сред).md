## 🏗️ 1. Иерархия: Домены, Деревья, Леса

|Термин|Суть|Аналогия|Практическое значение|
|---|---|---|---|
|**Домен (Domain)**|Логическая группа объектов (ПК, пользователи) с единой базой данных (AD DB), политиками безопасности и пространством имён (`corp.local`)|Офис компании с единым пропуском и правилами|Граница применения политик, репликации, администрирования|
|**Дерево (Tree)**|Иерархия доменов с общим пространством имён (`corp.local` → `sales.corp.local` → `eu.sales.corp.local`)|Филиалы одной компании с единым брендом|Делегирование управления, масштабирование без разрыва доверия|
|**Лес (Forest)**|Совокупность одного или нескольких деревьев с общей схемой (schema), конфигурацией и глобальным каталогом (Global Catalog)|Холдинг с разными брендами, но единым HR и ИБ-политиками|**Граница безопасности**: администратор леса = полный контроль над всеми доменами|
📌 **Ключевое правило:**
> 🔐 **Лес — это граница безопасности.** Доверие между лесами не передаётся транзитивно по умолчанию. Если вы не доверяете лесу — вы изолированы от него.
### Типы доверия (Trusts)
- **Transitive (транзитивное)**: `A доверяет B`, `B доверяет C` → `A автоматически доверяет C` (внутри леса — всегда).
- **Non-transitive**: доверие только между двумя конкретными доменами (между лесами).
- **One-way / Two-way**: кто кому разрешает доступ к ресурсам.
## 👥 2. Объекты: Пользователи, Группы, Подразделения (OU)
### 🔹 Пользователи (Users)
- Учётная запись + атрибуты (логин, пароль, отдел, телефон).
- Хранятся в домене, аутентифицируются через DC.
### 🔹 Группы (Groups) — основа управления правами

|Тип группы|Область действия|Для чего используется|
|---|---|---|
|**Security**|Domain Local / Global / Universal|Назначение прав доступа к файлам, принтерам, приложениям|
|**Distribution**|Только для рассылки в Exchange|Не для прав, только для почты|
📌 **Стратегия AGDLP** (Best Practice для прав доступа):
	A (Accounts) → G (Global groups) → DL (Domain Local groups) → P (Permissions)
### Подразделения (Organizational Units — OU)
- **Контейнеры для организации объектов**, а не для назначения прав!
- На них применяются **Group Policy**.
- Иерархия может отражать структуру компании:  
    `OU=Company → OU=Departments → OU=IT → OU=Workstations`
## ⚙️ 3. Group Policy (GPO) — централизованное управление
### 🔹 Что такое GPO?
Набор настроек, которые **принудительно применяются** к пользователям и компьютерам в определённой области (сайт/домен/OU).
### 🔹 Обработка политик (порядок применения — LSDOU):
	Local → Site → Domain → OU (вложенные: родитель → дочерний)
- Последняя применённая политика «побеждает» при конфликте.
- Можно использовать **блокирование наследования** и **принудительное применение (Enforced)**.
### 🔹 Типы настроек:

|Категория|Примеры|
|---|---|
|**Computer Configuration**|Установка ПО, скрипты запуска, настройки брандмауэра, требования к паролям|
|**User Configuration**|Переменные среды, отображение рабочего стола, ограничения на запуск программ|

🛠 **Полезные команды:**

**Проверить информацию примененных политик на устройство или пользователя**
gpresult /R

**Применить политики немедленно**
gpupdate /force

**Просмотреть применённые политики на клиенте**
gpresult /r          # кратко
gpresult /h report.html  # детальный отчёт в HTML

**На стороне сервера: найти неприменённые политики**
Get-GPOReport -All -ReportType Html -Path "C:\GPO_Report.html"

📌 **Совет по безопасности:**  
Никогда не редактируйте `Default Domain Policy` напрямую. Создавайте новые GPO с понятными именами (`GPO_Win10_SecurityBaseline`).
## 🔐 4. Аутентификация: Kerberos vs NTLM
### 🔹 Kerberos (стандарт в домене)
**Протокол с билетами (tickets) и доверенной третьей стороной — KDC (Key Distribution Center), работающим на каждом DC.**
#### Упрощённая схема входа:
1. Клиент → KDC: "Я пользователь ivan, хочу доступ к fs.corp.local"
2. KDC → Клиент: TGT (Ticket Granting Ticket), зашифрованный паролем пользователя
3. Клиент → KDC: TGT + запрос на доступ к сервису (файловому серверу)
4. KDC → Клиент: Сервисный билет (ST), зашифрованный ключом сервиса
5. Клиент → Сервис: ST + аутентификатор (время)
6. Сервис расшифровывает билет → доступ разрешён
✅ Преимущества:
- Взаимная аутентификация (клиент и сервер проверяют друг друга)
- Делегирование прав (Constrained Delegation)
- Защита от replay-атак (временные метки)
### 🔹 NTLM (устаревший, но ещё встречается)
**Challenge-Response протокол без участия третьей стороны.**
1. Клиент → Сервер: "Хочу войти как ivan"
2. Сервер → Клиент: Случайное число (challenge)
3. Клиент → Сервер: Хеш(пароль + challenge)
4. Сервер проверяет хеш локально или пересылает на DC
❌ Недостатки:
- Уязвим к атакам (Pass-the-Hash, NTLM Relay)
- Нет делегирования
- Медленнее при множественных запросах
### 🔹 Когда используется NTLM, даже если есть Kerberos?
|Ситуация|Причина|
|---|---|
|Доступ по **IP-адресу** (`\\192.168.1.10\share`)|Нет SPN (Service Principal Name) для привязки к сервису|
|Работа с **не доменными** устройствами (рабочая группа)|Нет доверия с доменом|
|Устаревшие приложения|Не поддерживают Kerberos API|
|Блокировка портов (Kerberos использует UDP/TCP 88)|Сетевые ограничения|
🛠 **Проверка типа аутентификации:**
**На клиенте: посмотреть сессии**
	klist sessions
**На сервере: включить аудит успешных входов (через GPO) и анализировать:**
Событие 4624 в журнале Security:
- Logon Type: 3 (сеть), 10 (удалённый рабочий стол)
- Authentication Package: Kerberos / NTLM

**🧩 Как всё это работает вместе? (Сценарий входа пользователя)**
1. Пользователь вводит логин/пароль на доменном ПК
2. ПК находит DC через DNS-запрос _ldap._tcp.dc._msdcs.corp.local
3. Запускается Kerberos: получение TGT
4. Применяются GPO из домена и OU, где находится компьютер
5. При доступе к сетевому ресурсу: получение сервисного билета
6. Права доступа проверяются через членство в группах (AGDLP)
7. Все события логируются в DC для аудита
## 🛡️ Безопасность: что важно помнить
1. **Защита учётных записей администраторов**:
    - Отдельные группы (`Domain Admins`, `Enterprise Admins`) — минимальный состав.
    - Запрет интерактивного входа на обычные ПК.
    - Использование **Privileged Access Workstations (PAW)**.
2. **Регулярный аудит**:
**Найти пользователей с бессрочными паролями**
	Search-ADAccount -PasswordNotRequired -UsersOnly
**Найти неактивные учётки (>90 дней)**
	Search-ADAccount -AccountInactive -TimeSpan 90.00:00:00 -UsersOnly
3. **Не включать «все» в «Администраторы домена»** — используйте делегирование прав на уровне OU.
